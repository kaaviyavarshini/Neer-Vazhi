## Project purpose
Browser visualisation showing where rain pools in the Thoraipakkam–Perungudi
stretch of OMR and Pallikaranai, Chennai. Five-scene narrative built on
CesiumJS + Google Photorealistic 3D Tiles + real DEM / OSM / rain data.
**This is a visualisation, not an engineering flood model. Say so in the UI.**

## Stack (never change without asking)
- Plain HTML + ES modules. No framework, no bundler.
- CesiumJS 1.117 from CDN (pinned). Google tiles via
  Cesium.createGooglePhotorealistic3DTileset with Cesium.GoogleMaps.defaultApiKey.
- No Cesium ion token: globe off, no default imagery, no geocoder.
- Python 3 scripts in /scripts for downloads and preprocessing
  (requests, numpy, rasterio).
- Heavy simulation loop in a Web Worker (pooling.worker.js).
- Served with `python -m http.server 8765 --directory web`.

## Coding rules
1. Never print, log or commit API keys. .env and web/js/config.js are git-ignored.
2. Small single-purpose modules. Max ~200 lines per JS file.
3. After each change: run what you changed, then say exactly what to open and what to see.
4. Units: metres, millimetres of rain, WGS84 lon/lat.
5. Comment every height-datum conversion.
6. Keep README.md's file list current with every new file.
7. Stubs must have a `// TODO` or `# TODO` marker so grep finds them.

## Run order (fresh clone)
```
python scripts/make_config.py     # 1. write web/js/config.js
python scripts/fetch_dem.py       # 2. download DEM
python scripts/fetch_roads.py     # 3. download roads
python scripts/fetch_rain.py      # 4. download rain
python scripts/build_grid.py      # 5. build JSON for the web app
python -m http.server 8765 --directory web   # 6. serve
# open http://localhost:8765/story.html
```

## Phase 2 rules
These apply to all Phase 2 work and take priority over anything above that conflicts.

1. **Never invent data.** Every dataset must come from a real file or URL and be
   recorded in `data/SOURCES.md` (name, URL, date downloaded, licence, notes).
   If data is missing, STOP and tell the user exactly what to download. Do not
   fill gaps with placeholder, "typical" or made-up values.
2. **Every assumption lives in `config/area.json`**, with a comment explaining it.
   This covers the runoff coefficient, drain capacity, outlet capacity and any
   similar tuning value. Never hard-code an assumption in a script or JS module.
   JSON has no comments, so give each assumption a matching entry in a `_notes`
   object in the same file (key = field name, value = what it is, why that value,
   and its source or "assumption"). Scripts and the browser ignore unknown keys.
3. **Validation and complaint data are ONLY for scoring the model**, never model
   inputs. Keep them in `data/validation/`; only scoring code may read them. The
   model (`pooling-core.js`, `pooling.worker.js`, `build_grid.py`) must not.
4. **Every loading step must show an on-screen error if it fails.** No endless
   spinners. Use a fetch timeout, report failures with `window.__bootFail(msg)`
   and signal success with `window.__bootReady()` (see `web/js/boot-guard.js`).
5. **After each step:** run the tests, tell the user exactly what to open and
   what they should see, and list any assumptions you made.
